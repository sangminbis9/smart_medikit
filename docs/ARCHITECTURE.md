# 시스템 구조와 담당 경계

> **상세 요구사항의 최종 기준:** [`../plan.md`](../plan.md). 이 문서는 **각 팀원이 어디까지 책임지는지**에 집중한다.

## 1. 전체 데이터 흐름

```text
[약 상자 / 처방약 봉투]
    ↓ 뚜껑 카메라 제시 (앱 사전 등록 불필요)
[Raspberry Pi / Python / OpenCV]
  - 개폐 센서, RGBW LED, 영상 안정화, 세션당 포장 촬영 1회
  - 뚜껑 닫힘 후 내부 이미지 촬영, 순차 로컬 큐
    ↓ S3에 이벤트 단위 업로드
[Amazon S3 → Lambda 컨테이너(ECR)]
  - PaddleOCR + OpenCV, 포장 후보 탐색, 최초 등록 또는 기존 포장 매칭
  - 식약처 제품정보, DUR 안전정보 연계
    ↓
[Lambda + DynamoDB]
  - 반입/반출, 재고/복약 추정, 안전정보·만료일, 이벤트 멱등성
  - 보류·정정 이력 저장 및 복용 알림 예약
    ├─ API Gateway WebSocket → 실행 중인 Flutter 앱 실시간 갱신
    └─ SNS → FCM/APNs → 등록된 전체 스마트폰 푸시
[Flutter Android/iOS + Three.js(WebView)]
  - 약품 목록, 실시간 3D, 복약, 재고, 확인 요청, 알림
```

## 2. 3인 개발 경계

| 영역 | 담당 | 입력 | 출력 / 책임 |
|---|---|---|---|
| `hardware/` | Raspberry Pi / 비전 | 개폐 센서, 카메라 | 촬영 세션, 전처리 이미지, 안정적인 로컬 전송 큐, LED |
| `backend/` | AWS / OCR / DB | 세션 이미지, 외부 의약품 데이터, 앱 요청 | 제품 식별, 상태 갱신, 재고/복용 추정, API, 실시간 이벤트, 알림 |
| `mobile/` | Flutter / 3D | 조회 API, 실시간 이벤트, 푸시 | Android/iOS 화면, 추가 촬영, 확인·수정, 3D 박스 뷰 |

- 공통 API·이벤트 변경은 `docs/CONTRACTS.md`를 먼저 갱신하고 세 영역 담당자가 리뷰한다.
- 권한·외부 API·인식 가중치·AWS 자원은 실제 구현 가능 여부를 검증한 뒤 확정한다.

## 3. 절대 혼동하지 않을 상태

- **촬영:** 로컬 이미지 확보 성공 여부. 파란 LED는 촬영 완료일 뿐 최종 식별 성공이 아니다.
- **식별:** 등록 포장 중 유일하게 매칭되었는지 / 새 제품으로 자동 등록되었는지 / 확인 대기인지.
- **입출고:** 기존 보관 상태 기반 추정. 실제 이동을 항상 증명할 수 있는 것은 아니다.
- **복용:** 반출과 실제 복용은 다르다. 복용 이력은 추정/사용자 확인을 분리한다.
- **재고:** 정제·캡슐의 수량은 예상치. 시럽·연고·파스·가루약 등은 잔여량 표시와 차감을 하지 않는다.
- **유효기간:** 실물에 명시된 실제 만료일과 `첫 반입일 + 품목 일반 사용기간` 임시 관리 기준일을 구분한다.
- **3D 위치:** X/Y는 관측 위치, Z는 추정 높이. 관측 불가 시 기존 추정값과 불확실 표시.
- **안전정보:** 현재 보관 중인 약품끼리 검사하는 기능과, 같은 날 반출 약품의 위험 조합을 비교하는 기능은 별개다.

## 4. 출시 범위와 제외 기능

- **단일 Raspberry Pi 기반 프로토타입 1대.** 개발팀이 Wi-Fi·AWS 연동을 미리 설정한다.
- Flutter 앱은 회원가입·초대코드·보관함 페어링 없이 테스트용 단일 보관함 데이터를 연다.
- 약품 식별 스티커/ArUco/QR코드 부착과 실제 포장 사진을 3D 텍스처로 렌더링하는 기능은 제외한다.
- 인증 없는 공개 쓰기 API나 실제 개인정보를 수집하는 공개 서비스로 출시한다고 가정하지 않는다.
