# PC 카메라 입력 실험

Raspberry Pi 카메라가 도착하기 전에 iPhone의 DroidCam 영상을 OpenCV로 읽어 보는 실험이다. `camera_preview.py`는 실시간 미리보기, **수동 방향 보정과 프레임 저장**, `--detect` 선택 시 **YOLOE-26n 포장 후보 탐지·사진 품질 검사·박스 영역 잘라내기 저장**을 제공한다. 자동 촬영 판단, Pi 카메라·센서·LED, AWS 전송은 아직 연결하지 않았다. 이 코드는 `plan.md`의 최종 촬영 상태 머신을 대신하지 않는다.

실제 Pi용 자동 촬영·GPIO·영속 큐 코드는 [`Raspberry_Pi/`](../Raspberry_Pi/README.md)에 별도로 있다. 이 폴더의 수동 촬영·품질 검사 실험을 Pi 실행 흐름에 통합한 상태는 아니다.

## 환경과 설치

- 현재 개발 환경: Windows, Python 3.14.0, OpenCV 5.0.0 (`opencv-python` 패키지 5.0.0.93), NumPy 2.5.4.
- iPhone의 DroidCam 앱과 Windows의 DroidCam Client를 켜고, PC 클라이언트에 영상이 보이는 상태로 둔다.
- OpenCV는 클라이언트가 제공하는 가상 웹캠을 읽는다. 아이폰의 초점·노출·사진 셔터를 제어하는 코드는 아니다.
- `requirements.txt`는 이 **PC 실험 환경**의 버전 목록이다. Pi 환경의 설치 방법은 실기기 연결 시 별도로 확인한다.

저장소 루트의 PowerShell에서 실행한다. 앞서 `.venv`를 만들었다면 생성 명령은 다시 실행하지 않아도 된다.

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r hardware/requirements.txt
```

가상환경은 별도 활성화 없이 위와 같이 해당 Python 경로를 직접 사용한다. `.venv/`는 Git에서 제외된다. OpenCV가 카메라 입력·화면 표시·JPEG 인코딩을 담당하며 NumPy는 프레임 배열을 다룬다. YOLOE에는 Ultralytics·PyTorch·Torchvision을 사용하고, Pillow로 한국어 탐지 라벨을 표시한다. 기존 웹 의존성만으로는 이 기능을 실행할 수 없어 Python 설치 목록을 추가했다. `--detect`를 생략한 기본 미리보기는 모델을 불러오지 않는다.

## 미리보기 실행

2026-10-26 사용자 실행에서 `dshow`로 카메라 0번 열기는 실패했고, 아래 `msmf` 명령으로 영상 표시와 JPEG 저장을 확인했다. 새로 추가한 회전 및 화면 맞춤 동작은 실제 영상으로 추가 확인해야 한다.

```powershell
.\.venv\Scripts\python.exe hardware/camera_preview.py --camera 0 --backend msmf
```

기본 카메라 번호는 `0`이다. `smart_medikit` 창에 아이폰 대신 노트북 카메라가 보이거나 열기에 실패하면 종료한 뒤 번호를 바꾼다. 카메라 번호는 PC마다 다르며 프로그램이 DroidCam을 이름으로 자동 선택하지는 않는다.

```powershell
.\.venv\Scripts\python.exe hardware/camera_preview.py --camera 1 --backend msmf
```

필요하면 번호를 `2` 등으로 바꾸어 확인한다. 옵션을 생략했을 때 Windows의 기본 입력 방식은 여전히 `dshow`이므로 현재 PC에서는 `--backend msmf`를 함께 지정한다.


| 조작 | 동작 |
|---|---|
| 영상 창을 선택하고 `R` | 시계 방향으로 90도 회전, 네 번 누르면 원래 방향 |
| 영상 창을 선택하고 `S` | 기본 모드: 전체 프레임 저장. `--detect`: 여백을 포함한 박스 영역 저장 또는 대상 선택 |
| 영상 창을 선택하고 `Q` 또는 `Esc` | 미리보기 종료 |
| 창의 닫기 버튼 | 미리보기 종료 |
| 터미널에서 `Ctrl+C` | 실행 중단 및 자원 정리 |

키 입력이 반응하지 않으면 영상 창에 포커스를 두고 영문 입력 상태에서 시도한다. 저장 결과와 오류는 PowerShell에 표시된다. 연결이 끊겨 새 프레임을 받지 못하면 종료하므로, DroidCam을 다시 연결한 뒤 명령을 재실행한다. 저장에 실패한 경우에는 오류를 알리고 미리보기를 유지한다.

## 글자 방향 맞추기

1. DroidCam에서 앞서 적용한 Transform의 회전·반전·잘라내기를 기본 상태로 되돌리고, 테스트할 동안 휴대폰을 한 방향으로 둔다. 이미 입력 영상에 생긴 검은 여백이나 잘린 영역은 Python에서 회전해도 복구되지 않는다.
2. 글자가 있는 테스트 상자를 정상 방향으로 세운다. 우리 영상 창에서 `R`을 눌러 글자가 똑바로 보이게 맞춘 다음 `S`로 저장한다. 저장 파일에서도 방향과 글자, 포장 가장자리가 정상인지 확인한다.
3. PowerShell에 표시된 회전 각도를 다음 실행의 `--rotate`에 지정하면 같은 보정을 적용한다. 예를 들어 시계 방향 90도 보정은 다음과 같다.

```powershell
.\.venv\Scripts\python.exe hardware/camera_preview.py --camera 0 --backend msmf --rotate 90
```

미리보기는 잘라내거나 늘이지 않고 가로 960·세로 720픽셀 이내로 비율을 유지해 표시한다. 탐지 모드에서는 전체 높이 720픽셀 안에 하단 품질 패널 220픽셀을 확보하므로 영상 표시 높이는 최대 500픽셀이다. 패널 글자는 함께 축소하지 않는다. 사진에는 표시용 축소를 적용하지 않으며, 회전은 전체 픽셀을 보존하고 90/270도에서는 사진의 가로·세로 크기가 서로 바뀐다. 입력에 포함된 여백은 임의로 잘라내지 않는다.

이 기능은 **수동 입력 방향 보정**이다. 휴대폰의 가로·세로 자세나 약품 포장의 글자 방향을 자동 감지하지 않고, OCR 성공도 판정하지 않는다. 휴대폰 방향을 바꾸면 다시 맞춰야 하며, 회전만으로 좌우가 뒤집힌 글자를 고칠 수는 없다. 실제 Pi의 고정 카메라 방향과 AWS OCR의 회전 대응은 별도로 검증한다.

## YOLOE-26n으로 포장 후보 찾기

모델은 텍스트 프롬프트를 지원하는 `yoloe-26n-seg.pt`를 사용한다. `-pf` 모델과 다르다. `package_detector.py`는 모델 준비·프레임 탐지·좌표에 따른 잘라내기·표시를, `image_quality.py`는 사진 한 장의 품질 수치·주의 사유 계산을, `camera_preview.py`는 카메라·회전·키 입력·사진 저장과 검사 연결을 맡는다.

```powershell
.\.venv\Scripts\python.exe hardware/camera_preview.py --camera 0 --backend msmf --detect
```

앞서 맞춘 회전 각도가 있다면 같은 명령 뒤에 `--rotate 90` 등을 추가한다. 모델 준비가 끝나면 영상 창이 열리고 번호·박스·범주·탐지 점수가 표시된다. `S`는 **10% 여백을 포함한 박스 영역을 원본에서 잘라 JPEG로 저장**한다. 저장 사진에는 박스·번호·라벨을 그리지 않으며 표시용 축소도 적용하지 않는다. 추론 자체에 오류가 나면 장치와 창을 정리하고 종료한다.

| `S`를 눌렀을 때 | 동작 |
|---|---|
| 후보 1개 | 그 박스 영역을 바로 저장 |
| 후보 여러 개 | 해당 프레임을 멈추고 첫 후보를 노란색으로 강조. `Tab`으로 다음 후보, `Enter`로 선택한 영역 저장 |
| 후보 없음 | 안내만 출력하고 저장하지 않음 |
| 대상 선택 중 `Esc` | 저장을 취소하고 실시간 미리보기로 복귀 |
| 대상 선택 중 `Q` 또는 창 닫기 | 저장하지 않고 프로그램 종료 |

대상 선택 중에는 새 프레임을 읽거나 다시 추론하지 않는다. 화면에 고정된 프레임의 원본과 좌표를 함께 사용하므로 선택 도중 대상이 바뀌지 않는다. 선택 후에는 실시간 미리보기를 재개한다. 이 선택 과정은 **PC에서 잘라내기를 확인하는 수동 실험**이며, 최종 Pi의 자동 촬영 대상 선택 규칙은 아직 구현하지 않았다. `--detect`가 없는 기본 모드는 기존처럼 전체 프레임을 저장한다.

표시와 저장에 사용하는 박스는 검출된 너비·높이의 **10%를 각 방향에 추가**한다. 예를 들어 200×300픽셀 박스는 좌우 각 20·위아래 각 30픽셀을 더해 240×360픽셀로 자른다. 소수점 좌표는 바깥쪽으로 반올림한다. 화면 경계에서는 확보 가능한 영역까지만 자르고 여백 부족을 품질 패널과 저장 안내에 표시한다. 이는 포장 전체가 포함됐다는 보장이 아니며 화면 밖이나 가려진 내용은 복구하지 않는다. 아래의 품질 검사는 주의 안내이며 자동 촬영·저장 차단 기준으로 연결하지 않았다.

| 탐지 요청 표현 | 화면 표시 |
|---|---|
| `medicine box` | 약품 상자 |
| `prescription medicine bag` | 처방약 봉투 |
| `medicine sachet` | 소형 약품 포장 |
| `pill blister pack` | 알약 블리스터 포장 |
| `medicine bottle` | 약품 병 |
| `ointment tube` | 연고 튜브 |
| `medical patch package` | 파스 포장 |
| `paper document` | 문서 후보 |

이 목록은 추가 학습된 정답 범주가 아니라 **찾도록 요청하는 텍스트**다. 일반 상자·병·문서가 검출될 수 있으며 약품 여부나 처방전의 진위를 판정하지 않는다. 박스가 생겼다는 사실은 촬영 준비 완료나 식별 성공을 뜻하지 않는다. 탐지 점수도 약품 식별 정확도가 아니다. 기본 문턱값은 실험용 `0.25`이며 `--conf 0.4`처럼 조정할 수 있다. 낮추면 후보와 오탐이 함께 늘 수 있다.

- 첫 준비에는 인터넷이 필요하다. CLIP 패키지는 확인한 공식 Git 커밋을 설치 목록에 고정했으므로 패키지 설치에 Git도 필요하다. 모델 외에 약 254MB의 `mobileclip2_b.ts` 텍스트 인코더를 내려받는다. 텍스트 범주는 시작할 때 한 번 설정한다.
- 모델·텍스트 인코더·Ultralytics 설정은 Git에서 제외된 `local_data/models/yoloe/`에 둔다. 준비 실패 시 카메라를 열지 않고 오류를 알린다.
- CPU에서 현재 프레임을 분석한 뒤 그 프레임에 박스를 표시한다. 다른 프레임의 오래된 박스를 재사용하지 않는다. CPU 처리 시간이 길면 미리보기 갱신과 키 응답도 느려질 수 있고, 카메라 드라이버 내부의 영상 지연은 별도 검증이 필요하다.
- 한글 폰트를 찾으면 한국어로 표시하고, 없으면 영문 탐지 표현으로 표시한다. 실제 촬영 시험에서는 손만 보이는 장면, 배경에 비슷한 상자가 있는 장면, 포장의 일부가 가려지거나 화면 끝에 걸린 장면도 확인한다.
- 현재 코드는 로컬 추론과 품질 측정만 수행한다. Pi 5 4GB에서의 처리 속도·메모리, 자동 촬영 조건 판단 및 S3 전송은 아직 검증·구현하지 않았다.

## 사진 품질 검사

위의 `--detect` 명령에 자동으로 포함되며 추가 설치나 옵션은 없다. 탐지한 **10% 여백 포함 영역의 원본 픽셀**을 검사하고, 영상 아래 별도 패널에 **양호/주의(실험 기준)**와 수치를 표시한다. `--detect`를 생략하면 기존 전체 프레임 미리보기·저장만 수행한다.

- 후보가 하나이면 그 영역의 품질을 실시간으로 표시한다. 여러 개이면 `S`로 고정한 다음 `Tab`으로 선택한 대상의 결과를 보여준다. 고정된 화면을 선택하는 동안 재추론·재측정하지 않는다.
- 대상이 없으면 ‘대상 없음’이며 양호로 표시하지 않는다. 품질 검사 오류가 나면 이전 결과를 재사용하지 않고 장치를 정리한 뒤 종료한다.
- **주의가 있어도 `S`/`Enter` 수동 저장은 가능**하다. 실제 결과와 비교하기 위한 실험이며 자동 촬영·재촬영·저장 차단은 하지 않는다. 저장할 때 같은 원본 영역의 수치와 사유를 터미널에도 출력한다.
- 사진에는 품질 패널·박스·라벨을 넣지 않는다. JPEG 품질 설정 `95`, 저장할 영역의 해상도와 기존 파일명은 유지한다. 별도 결과 파일이나 업로드는 만들지 않는다.

초기 기준은 아래와 같으며 **실측으로 보정된 합격 기준이 아니다**. 조정할 때는 `image_quality.py`의 `QualityThresholds` 기본값을 수정하고 재실행한다. 별도 호출부에서는 `assess_photo(..., thresholds=QualityThresholds(...))`로 전달할 수도 있다.

| 지표 | 측정 방법 | 초기 주의 조건 |
|---|---|---|
| 선명도 | 회색조 이미지의 `cv2.Laplacian(..., CV_64F).var()` | `100` 미만이면 흐림 의심 |
| 평균 밝기 | 회색조 픽셀의 평균, 범위 0~255 | `50` 미만 또는 `210` 초과 |
| 어두운 부분 | 밝기 `30` 이하 픽셀 비율 | `30%` 초과이면 어두움 의심 |
| 밝은 부분 | 밝기 `245` 이상 픽셀 비율 | `20%` 초과이면 과노출·반사 의심 |
| 원본 영역 크기 | 저장할 crop의 실제 가로·세로 | 짧은 변이 `160px` 미만 |
| 여백 부족 | 10% 확장 영역이 화면 경계에 걸렸는지 | 걸렸으면 별도 주의 |

평균 밝기 또는 픽셀 비율 중 하나라도 해당하면 노출 주의를 표시한다. 계산 비용을 제한하기 위해 **측정용 이미지만 긴 변 640픽셀 이내로 비율 축소**하며, 작은 이미지는 확대하지 않는다. 저장할 사진은 이 측정용 배열로 바꾸지 않는다. 위 선명도 기준은 이 계산 방식에서만 비교해야 하며 해상도·구도·글자 수·배경·노이즈·DroidCam 워터마크에도 영향을 받는다.

밝은 흰 포장도 과노출·반사 의심이 될 수 있다. 작은 크기와 여백 경고가 없다는 사실도 글자가 충분히 크거나 포장 전체가 포함됐다는 증거는 아니다. **양호는 현재 주의 조건에 해당하지 않는다는 뜻**이고, 시간에 따른 안정성·약품 여부·글자의 읽기 가능성·OCR 성공을 보장하지 않는다. 자동 밝기 보정, 선명화, 워터마크 제거, 연속 프레임 추적과 자동 촬영은 추가하지 않았다.

수동 확인은 개인정보가 없는 같은 포장을 정상 초점·흐림·어두운 조명·강한 반사·먼 거리로 바꿔 보여주면서 수치와 사진을 비교한다. 주의 상태에서도 저장되는지, 여러 후보를 선택했을 때 해당 사진의 결과인지 확인한다. 실제 Pi 카메라에서는 조명과 입력 해상도가 달라지므로 기준을 다시 조정해야 한다.

## 저장 사진과 프로젝트 경계

- 저장 위치는 실행한 폴더와 관계없이 저장소의 `local_data/camera_captures/`다. 이 폴더는 기존 `.gitignore`에 의해 Git에서 제외된다.
- `S`를 누르기 전에는 사진 파일이나 저장 폴더를 만들지 않는다. 별도의 영상 녹화나 서버 업로드도 하지 않는다.
- 파일명은 전체 사진 `frame_...jpg`, 잘라낸 사진 `crop_...jpg`로 구분하며 시간과 임의 식별자를 포함해 기존 사진을 덮어쓰지 않는다. 잘라내기 저장 시 별도의 전체 사진은 추가 저장하지 않는다. 한국어 Windows 경로를 지원하도록 JPEG 인코딩 후 Python으로 파일을 저장한다.
- 저장 사진은 **PC로 전달된 영상 프레임에 선택한 회전을 적용한 이미지 또는 그 일부 영역**이다. 아이폰 기본 카메라의 고해상도 원본 사진과 다르며, 클라이언트에서 적용한 회전·확대 등의 영향도 받을 수 있다.
- 저장 성공은 좋은 화질이나 정확한 약품 식별을 의미하지 않는다. 이번 수동 저장은 입력 실험이며 세션·입출고 이벤트를 만들지 않는다.
- 개인정보가 없는 포장이나 합성 자료로만 시험한다. 실제 처방전이나 환자 정보는 사용하지 않는다. 테스트 사진은 필요한 확인이 끝나면 사용자가 삭제한다.

나중에 Pi로 옮길 때 카메라 입력·실제 정지 사진 촬영은 Picamera2로 연결한다. 탐지 모듈은 이미지 프레임을 입력으로 받지만, 이번 설치 목록과 처리 속도를 Pi에서도 그대로 쓸 수 있다고 가정하지 않는다.

## 검증

실제 카메라를 열지 않는 테스트는 표준 `unittest`를 사용한다. 카메라·화면 함수는 모의 객체로 대체하고, 파일 저장은 합성 이미지만 사용한다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s hardware/tests -v
.\.venv\Scripts\python.exe -m py_compile hardware/camera_preview.py hardware/package_detector.py hardware/image_quality.py hardware/tests/test_camera_preview.py hardware/tests/test_package_detector.py hardware/tests/test_image_quality.py
.\.venv\Scripts\python.exe hardware/camera_preview.py --help
.\.venv\Scripts\python.exe -m pip check
```

테스트 항목은 카메라 선택·잘못된 번호/각도/점수·열기 실패·프레임 단절·빈 프레임·회전 방향·표시/저장 방향 일치·원본 해상도의 영역 저장·저장 실패·종료 자원 해제·한국어 경로의 JPEG 저장/재읽기·모델 준비 실패·탐지 예외·원본과 박스 표시 분리·모델 캐시 경로 복원·박스 경계·고정 프레임 대상 선택·후보 없음·선택 취소다. 실기기에서는 영상 출처, `R` 회전과 비율, 탐지 박스가 포장 전체를 포함하는지, `S` 저장 사진에 박스가 없는지, 여러 후보의 `Tab`/`Enter`/`Esc`, `Q`/창 닫기, Wi-Fi 단절 안내를 확인해야 한다.

2026-10-26 YOLOE 연결 후 자동 테스트 27개, Python 문법 검사, `--help`, `pip check`, `git diff --check`가 통과했다. 제한된 실행 환경에서는 임시 파일 경로를 Git 제외 폴더인 `local_data/test_tmp/`로 지정했다. 패키지 설치 후 실제 공식 모델과 텍스트 인코더를 준비하고 640×480 합성 빈 프레임으로 CPU 추론을 실행해 반환 크기·입력 보존·한국어 글꼴 선택을 확인했다. 이는 약품 탐지 정확도 검증이 아니다. 사용자는 기존 `msmf` 영상 표시와 JPEG 저장을 확인했으며, 변경 후 실제 카메라·GUI·약품 포장 탐지는 사용자 확인이 남아 있다.

현재 Python 3.14.0 / Torch 2.14.1에서는 텍스트 인코더를 읽을 때 `torch.jit.load`의 Python 3.14 이상 지원에 관한 `FutureWarning`이 출력된다. 이번 모델 준비와 합성 추론은 완료됐지만, 이 경고를 무시하고 향후 패키지 호환성까지 보장하지 않는다. 버전을 변경할 때 모델 준비부터 다시 검증해야 한다.

같은 날 사용자는 실제 영상에서 탐지 박스 표시를 확인했고, 거리에 따라 범주명이 바뀌는 현상을 보고했다. 이후 각 방향 10% 여백과 수동 영역 저장을 연결했다. 자동 테스트 43개로 소수점 좌표의 바깥쪽 반올림, 화면 네 경계 제한, 마지막 행·열 보존, 잘못된 박스 제외, 원본 보존, 중복 추론 방지, 선택·취소·종료와 잘라낸 JPEG 크기를 검증했다. 잘라내기와 후보 선택의 실제 카메라·GUI 확인은 남아 있다.

2026-10-27 사용자는 실제 사진이 잘 저장된다고 확인했다. 이후 품질 검사 추가 후 합성 이미지·모의 카메라 기반 **63개 테스트**가 통과했다. 선명/흐림 비교, 국소 암부·밝은 부분, 입력·기준값 오류, 원본 보존, 회전·선택한 영역 측정, 주의 상태의 수동 저장, 검사 오류 종료, 품질 패널과 사진의 분리를 확인했다. 합성 품질 결과를 맑은 고딕으로 렌더링해 다섯 경고가 잘리지 않는 것도 확인했다. 새 품질 패널의 실카메라 조작·판정 정확도와 Pi 처리 속도는 검증하지 않았다.
